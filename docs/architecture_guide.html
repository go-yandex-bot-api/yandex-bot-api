1. Общая карта кодовой базы

Наша библиотека построена по стандарту Standard Go Project Layout с применением принципов Чистой Архитектуры (Clean Architecture). Логика разделена на независимые слои:

Ваш Код (bot / main.go)
⬇️
pkg/router (Роутер, Middleware, Хендлеры)
pkg/fsm (Память Состояний)
⬇️
api/messages
api/chats
api/polls
api/files
api/updates
⬇️
core/ (HTTP Клиент, Ретраи, Маскирование токенов)
⬇️
Яндекс Мессенджер API (botapi.messenger.yandex.net)
⚡
Пакет yabotapi (Корень)
Главный фасад для разработчика (точка входа). Содержит единый объект Bot и конструкторы.
🔌
Пакет core/
Низкоуровневое HTTP-ядро. Отвечает за вызовы, маскирование Authorization токенов, повторные попытки (Retry Jitter) и загрузку файлов.
🛠️
Пакет api/
Разбитые по смыслу сервисы Яндекса (сообщения, чаты, опросы, файлы, обновления).
🧠
Пакет pkg/
Вспомогательный высокоуровневый инструмент: Маршрутизатор (Router), FSM хранилище состояний, форматирование и пагинация.

2. Инициализация и Bot Core

Всё начинается в функции main() с вызова конструктора yabotapi.NewBot(...). Посмотрим, как это работает:

package main

import (
    "log"
    yabotapi "github.com/go-yandex-bot-api/yandex-bot-api"
)

func main() {
    // 1. Валидация токена и создание клиента
    bot, err := yabotapi.NewBot("YOUR_OAUTH_TOKEN", yabotapi.WithDebug(true))
    if err != nil {
        log.Fatalf("Ошибка инициализации бота: %v", err)
    }

    log.Printf("Бот успешно создан!")
}
💡 Что происходит внутри NewBot?
1. Проверяется токен (защита от пустого токена).
2. Создается изолированное HTTP-ядро core.Client.
3. Автоматически подключается logging_client.go, который скрывает секреты (заменяет `Authorization: OAuth token` на `***REDACTED***`).
4. Инициализируются все 6 сервисов API: bot.Messages, bot.Chats, bot.Files, bot.Polls, bot.Updates, bot.Users.

3. Сервисный слой API

Объект bot не является "God-объектом" со 100 методами. Вместо этого он агрегирует узкоспециализированные сервисы:

// 1. Отправка текста через сервис сообщений
bot.Messages.SendText(ctx, messages.SendTextRequest{
    ChatID: "chat_id_here",
    Text:   "Привет из Яндекса!",
})

// 2. Создание опроса через сервис опросов
bot.Polls.Create(ctx, polls.CreateRequest{
    ChatID:  "chat_id_here",
    Title:   "Какой стек вы используете?",
    Answers: []string{"Go", "Python", "Rust"},
})

// 3. Скачивание файла по ID напрямую
fileStream, err := bot.Files.GetFileByID(ctx, fileID)

4. Роутер и Механика Маршрутизации

Когда приходят сообщения или обновления от пользователя, метод resolveHandler(u) производит пошаговую приоритетную проверку (Routing Pipeline):

  • 1
    Нажатие Инлайн-кнопки (ServerAction): Проверяется u.BotRequest.ServerAction.Name в мапе buttonHandlers. Нажатие кнопки обрабатывается первым и НЕ проваливается дальше (no fallthrough).
  • 2
    Команда (/start, /help): Проверяется u.IsCommand() в мапе commandHandlers.
  • 3
    Состояние FSM (FSM State): Вычисляется ID отправителя, считывается текущий стейт из хранилища storage.Get(senderID) и ищется точное совпадение в stateHandlers или регулярное выражение в stateRegexpHandlers.
  • 4
    Специализированный контент (Vote, File, Image, Sticker): Проверяются события в порядке приоритета: u.Vote != nil ➔ HandleVote, u.File != nil ➔ HandleFile, len(u.Images) > 0 ➔ HandleImage, u.Sticker != nil ➔ HandleSticker.
  • 5
    Обычный текст (Text): Проверяется u.Text != "" ➔ вызов HandleText.
  • 6
    Запасной обработчик (Fallback): Если ни один обработчик не подошел ➔ вызывается HandleDefault.
r := router.NewRouter(bot)

// Команда /start
r.HandleCommand("start", func(c *router.Context) error {
    return c.Replyf("Привет, %s!", c.SenderLogin())
})

// Специализированный обработчик прикрепленных файлов
r.HandleFile(func(c *router.Context) error {
    return c.Replyf("Получен документ: %s", c.Update.File.Name)
})

4.1 Цепочка Middleware и Перехват (Onion Pattern)

Middleware в нашей библиотеке строится по классическому паттерну "Луковицы" (Onion Pattern). Каждая Функция-прослойка оборачивает следующую:

Обновление (Update)
⬇️
Middleware 1 (Логирование: ДО)
⬇️
Middleware 2 (Авторизация: ДО)
⬇️
Ваш Хендлер (Бизнес-логика)
⬆️
Middleware 2 (Авторизация: ПОСЛЕ)
⬆️
Middleware 1 (Логирование: ПОСЛЕ)

Пример прерывания цепочки (Interception):

Если Middleware возвращает ошибку или не вызывает next(c), цепочка прерывается, и ваш главный хендлер НЕ вызывается вовсе:

// Middleware проверки прав администратора
func AdminOnlyMiddleware(next router.HandlerFunc) router.HandlerFunc {
    return func(c *router.Context) error {
        // 1. Код ДО выполнения хендлера
        if !c.SenderLoginIs("admin_login") {
            _ = c.Reply("⛔ Доступ запрещен! Вы не администратор.")
            // НЕ вызываем next(c) — цепочка останавливается здесь!
            return nil
        }

        // 2. Передача управления следующему middleware или хендлеру
        err := next(c)

        // 3. Код ПОСЛЕ выполнения хендлера (например, замер времени)
        log.Printf("Запрос от админа обработан за %v", time.Since(start))
        return err
    }
}

r.Use(AdminOnlyMiddleware)

4.2 Несколько Роутеров и Работа с Каналами

Разработчики часто спрашивают: "Что произойдет, если я создам несколько объектов Router?"

Сценарий А: 2 Роутера на 1 Канал
Если запустить go r1.Start(ctx, updatesCh) и go r2.Start(ctx, updatesCh) на один и тот же канал сообщений updatesCh:
Канал в Go гарантирует, что каждое сообщение заберет ровно ОДИН успевший воркер. Сообщения распределятся между ними конкурентно. Срабатывать на одно сообщение оба роутера НЕ будут.
Сценарий Б: Модульный Роутинг (Рекомендуемый)
Если вам нужно разделить код большого бота на модули (например, AdminModule и CatalogModule), создается один главный Router, а хендлеры выносятся в отдельные пакеты и файлы функций, которые регистрируются на нем.

5. Состояния FSM и Generics

Для пошаговых сценариев (опросы, оформление заказа) используется FSM (Finite State Machine). Мы добавили поддержку Generics в метод router.GetFSMData[T]:

type Order struct {
    Item  string
    Count int
}

// Шаг 1: Установка состояния и данных
r.HandleCommand("order", func(c *router.Context) error {
    c.FSM().SetState("WAIT_ITEM")
    c.FSM().SetData("order_info", Order{Item: "Пицца", Count: 2})
    return c.Reply("Подтвердите заказ пиццы.")
})

// Шаг 2: Извлечение строго типизированных данных БЕЗ interface{} и паник
r.HandleState("WAIT_ITEM", func(c *router.Context) error {
    order, ok := router.GetFSMData[Order](c, "order_info")
    if !ok {
        return c.Reply("Ошибка состояния заказа.")
    }
    
    c.FSM().Clear()
    return c.Replyf("Заказ %s в количестве %d принят!", order.Item, order.Count)
})

6. Кнопки и KeyboardBuilder

Для создания интерактивных клавиатур поддерживаются легкие функции-конструкторы и динамический билдер:

// 1. Простая кнопка без данных (2 параметра):
btn1 := yabotapi.NewSimpleActionButton("Сказать привет", "btn_hi")

// 2. Кнопка с данными (3 параметра):
btn2 := yabotapi.NewActionButton("Купить", "btn_buy", 42)

// 3. Динамическая сборка сеток в цикле через KeyboardBuilder:
kb := yabotapi.NewKeyboardBuilder(true).Columns(2)
for _, product := range catalog {
    kb.AddButton(product.Name, "buy", product.ID)
}
keyboard := kb.Build()

c.ReplyWithKeyboardf(keyboard, "Выберите товар из каталога:")

7. Short-Polling и Webhooks

Яндекс Мессенджер поддерживает два метода получения событий:

Short-Polling (Jitter-Backoff)
Сервер Яндекса сразу закрывает соединение. Чтобы бот не уходил в "spin-loop" с 100% нагрузкой CPU, в api/updates/service.go встроен механизм Jitter Backoff с автоматическим сбросом интервала при получении событий.
Webhooks (MaxBytesReader)
Прием входящих HTTP POST запросов. Для защиты сервера от Out-Of-Memory (OOM) при больших атаках тело запроса ограничено через http.MaxBytesReader на 10 мегабайт.

8. Защита, OnError и Graceful Shutdown

Библиотека готова к высоким нагрузкам в Production:

// 1. Глобальный обработчик ошибок (bubble-up)
r.OnError(func(c *router.Context, err error) {
    log.Printf("Ошибка в хендлере для %s: %v", c.SenderLogin(), err)
    _ = c.Replyf("⚠️ Произошла внутренняя ошибка.")
})

// 2. Изящная остановка (Graceful Shutdown)
ctx, cancel := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
defer cancel()

// Запуск роутера с плавной доработкой всех запущенных воркеров через context.WithoutCancel
r.Start(ctx, updatesChannel)
⚠️ Автоматический recover() паник
Внутри роутера каждая горутина-воркер обернута в recover(). Если в одном из ваших обработчиков произойдет сбой или паника, весь бот НЕ упадет — роутер перехватит панику, выведет стектрейс в лог и продолжит работать дальше.
